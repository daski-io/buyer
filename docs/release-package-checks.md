# Release package checks

The buyer owns its challenge-to-signature contract and published package
layout. Release orchestration, exact live deployment identity and the
published CLI acceptance lane remain in the release coordinator. The
definition of done for develop and what each CI job proves are in
[release readiness](./release-readiness.md).

## Existing and strengthened coverage

The existing paymentIdentifier regressions already cover the September 3
sign-payment identifier replacement and September 4 buy identifier mismatch.
The actual buy-flow tests also prove quote approval, issued identifier echo,
exactly one signature, ambiguous submission recovery and refusal of changed
purchase terms. Scheme tests independently cover recipient, token, rail,
closed typed data, nonce recomputation and signature policy. These tests remain;
adding another helper test would not close the command-boundary gap.

The new tests in `packages/pay/test/buyFlow.test.ts` call the actual
`runSignPayment` command with an externally saved challenge, the existing
fixture context and the real policy/signing code. They verify the same issued
identifier in its result, payment extension and persisted order, no gateway
submission, and refusal of a second authorization. Wrong route and unsupported
rail are rejected before constructing the signer context. Context injection
matches the existing buy command's test seam; production still uses the same
context constructor. These tests use an isolated test key and never contact
a gateway or submit a payment.

## Build and packed artifact identity

`npm test` starts with the real package artifact regression. It removes only
the two generated dist directories, forces the existing TypeScript project
build, packs both workspaces without lifecycle scripts or registry access,
and verifies the tarball manifests and compiled bytes. Deleted source must
not leave stale JavaScript in a publishable package.

An isolated package layout uses the two extracted candidate tarballs with
lockfile-installed external dependencies. The smoke check runs the actual
packed CLI, checks its version, produces a `doctor --json` report offline from
an empty `DASKI_HOME` whose profile points at closed loopback ports, and
exercises invalid-challenge refusal before signer initialization. Withholding
the packed entrypoint must break the check; the checkout's CLI is never a
fallback. The test also changes compiled and packed bytes after qualification
to prove reuse is refused, then restores the exact generated bytes. No wallet,
RPC, model, paid conformance or npm publication occurs.

The generated `.scratch/package-proof/proof.json` binds:

- every tracked source/configuration/lockfile input by repository-relative
  path and SHA-256, with no absolute checkout path in content identity;
- actual Node, npm and TypeScript versions;
- every compiled output's SHA-256;
- package names, versions, exact packed filenames, SHA-256 and npm integrity;
- executed packed CLI boundaries and broken-entrypoint rejection.

`node scripts/package-artifacts.mjs --verify
.scratch/package-proof/proof.json` refuses changed source, toolchain, compiled
outputs or tarballs. CI uploads proof and packages separately for Node 20, 22
and 24. The release workflow checks this identity before its existing trusted
publication path. The proof is a candidate artifact proof; registry
installability, signatures/provenance, exact published package identity and
applicable paid acceptance remain separate release obligations.

The root CI's separate pre-test build was retired: package qualification owns
the one clean build, followed by the existing functional suite. Duplicate
identifier helper tests and a new live conformance gate were not introduced.
The package proof is a necessary net addition because a source-tree test cannot
establish which files npm will ship or whether the packed entrypoint resolves.
